Featured case study

LinkedIn Agent

An open-source assistant for a job search. It finds offers that match my profile, prepares a CV tailored to each one (LaTeX to PDF) and a draft email, and sends only after I have read and approved it.

Trust by design

Every number and claim must trace back to the master CV. The email's factual sentences are copied from the CV by code. The model only writes the subject, the opening and the closing.

Human in the loop

Dry-run is the default. To send, I retype the recipient address. Nothing is sent without an explicit approval.

Security mindset

Job pages and search results are treated as untrusted data, never as instructions to follow.

Individual project · Academic coursework

rag-invoices

Invoice question answering that combines LLM-extracted metadata with semantic search, so questions can mix meaning and exact conditions.
  • Qdrant
  • LangChain
  • Groq LLM
  • Pydantic
  • sentence-transformers

Problem

Totals, customers and line items are locked inside PDF layouts. Semantic search over raw text cannot reliably answer questions that mix meaning with exact conditions such as a date range, a total or a customer.

Solution

Ingestion turns each PDF into chunks that carry structured invoice metadata in Qdrant. At query time the question becomes a metadata filter plus a semantic query, and the answer is written only from what was retrieved.

My part

Individual coursework: I implemented the complete RAG pipeline myself, from metadata extraction to ingestion and chat.

Technical approach

  • Idempotent ingestion. Every file is hashed with SHA-256 and skipped if that hash is already in Qdrant. Work is saved every 20 invoices, an interrupted run saves what it has, and a Groq configuration error stops the run instead of silently skipping files.
  • Structured extraction. A Groq-hosted LLM at temperature 0 fills a Pydantic schema: invoice code, bill to, ship to, date, shipping, discount, total and line items. The prompt says to return null for missing fields and never invent values. Only the first 12,000 characters are sent.
  • Chunking and embeddings. Recursive splitting at 1,000 characters with 100 overlap. Each chunk keeps the invoice metadata. Embeddings come from all-MiniLM-L6-v2.
  • Indexed metadata. Qdrant payload indexes by type: keyword (invoice code, file hash), full text (customer, ship to, item names), float (total, discount, shipping) and integer (date as a timestamp).
  • Query planning. One LLM call extracts filters from the question (invoice code, customer, ship to, item, date range, total range, has discount), another rewrites it into a short search query.
  • Retrieval and answer. Filtered similarity search, top 5. If the filter returns nothing, the search is repeated without it. The answer prompt requires the invoice code and allows "I don't know".

AdForgeX

An integrated AI platform for advertising: it researches the market, the audience and the product image before it writes a single line of copy.
  • FastAPI
  • 6-step LLM pipeline
  • RAG · ChromaDB
  • Vision LLM
  • Playwright
  • React + TypeScript

Problem

Ad copy written from a product name alone ignores what competitors say, what buyers struggle with and what the product looks like. AdForgeX treats ad creation as research first, generation second.

Solution

One full-stack application that runs six chained steps, each using the output of the previous ones: product analysis, competitor intelligence, image analysis, audience insights, ad strategy, ad generation. The result is a hook, a caption, a call to action and visual recommendations.

My part

  • RAG-based automated replies to social media comments.
  • Sentiment analysis of comments with a Hugging Face sentiment model.
  • Automated comment management and response.

The rest of the platform (strategy selection, competitor analysis, content generation and the other components) is team work.

Technical approach

  • Orchestration. pipeline.py runs the six steps. Progress is streamed to the React dashboard over Server-Sent Events, one update per step.
  • Retrieval (RAG). ChromaDB holds high-performing ad patterns, embedded with all-MiniLM-L6-v2 and retrieved top-5 by default. Each finished run saves the scraped ads and image descriptions back, so the knowledge base grows.
  • Competitor intelligence. Playwright scrapes competitor product listings and reviews, with a configurable timeout (15 s by default).
  • Vision. A multimodal model (Llama 4 Scout through Groq) extracts visual selling points. A validation step detects an image that does not match the product before the full pipeline runs.
  • Text generation. Llama 3.3 70B through Groq. Prompt templates and step runners are kept in separate modules.
  • Platform. JWT authentication with SQLite, Docker Compose with development and production profiles, Nginx reverse proxy.

Team project · team of 4 · In progress

VishGuard

Real-time detection of vishing (voice phishing) from the call audio and its transcript, built by four people who each own one modality.
  • Multimodal fusion
  • XLM-R
  • wav2vec2 / Whisper
  • eGeMAPS
  • DVC

Problem

Detect vishing calls as they happen, across English, French and Arabic, and check that a model trained on synthetic calls still works on data it has not seen.

Team process

Four people, one per modality: text, self-supervised audio, prosody, and fusion with robustness. Two-week sprints, the first from 8 November 2026. Everyone works on a separate git branch.

My part so far

Audio embedding extraction with a pretrained audio model. The downstream classification model and the evaluation are not done yet.

Technical approach (team blueprint)

  • Data. VISHGUARD, a synthetic multilingual corpus of 3,059 calls in English, French and Arabic, versioned with DVC on S3. ASLC-448, an Arabic corpus, is kept as out-of-domain validation.
  • Modalities. Text with XLM-R, audio with wav2vec2 or Whisper embeddings, prosody with eGeMAPS features.
  • Fusion. Cross-attention between modalities, plus an audit of bias introduced by the text-to-speech used to make the synthetic calls.

Lessons from building

Three things that broke, and what I changed

The model rewrote my CV

What happened: in the first real run, the model turned "built" into "designing and deploying" and merged two facts into one sentence. My word-level check let it through.

What I changed: factual sentences are now copied from the master CV by code. The model writes only the subject, the opening and the closing.

Research that invented companies

What happened: a research run returned companies that were not in any source.

What I changed: capitalized names and job titles must now appear in a cited source, and any link or address missing from the master CV is refused as an unknown source.

A profile page that returned 500

What happened: saving the master CV created a half-empty profile row, and reading it crashed on the empty fields.

What I changed: safe defaults for every base field, plus regression tests for that path.
